System · the big picture

From three firmwares to one console

Today the games are standalone STM32 firmware images — each owns the CPU, the display driver, everything. The console turns them into cartridges behind a shell, on a shared hardware abstraction layer, ready to port to the Raspberry Pi Pico 2 (RP2350).

The idea

A game-select shell owns the hardware and the shared services, then launches the chosen game through a small lifecycle contract and takes control back when it exits:

  • init(ctx) — game grabs shared services, sets up state
  • update(input, dt) — one tick of game logic
  • render(fb) — draw into the shared framebuffer
  • teardown() — release, return to the shell

Each game stops owning main() and its own copy of the driver, and becomes a module the shell can list, launch, and reclaim.

Today — proof-of-concept cartridges

  • Two playable games (Spaceship, Paint) on STM32F411 @ 16 MHz
  • Each is a self-contained firmware image…
  • …with its own copy-pasted ST7735 / ADC / GPIO driver
  • No shell, and no way to exit a game yet

Where it’s headed — the console

  • Game-select shell + the cartridge lifecycle contract
  • One shared HAL / driver (one endianness, one code path)
  • DMA + framebuffer display service; seeded RNG; flash saves
  • Snake as the reference cartridge
  • Port to RP2350 — PLL/DMA done, PIO offloads the panel, RAM is a non-issue

Proof-of-concept framing

The missing shell and shared HAL are not oversights — they are the integrating features the console exists to add. Building each game standalone first de-risked the hard parts (driver, input, timing) independently; folding them into one runtime is the deliberate next phase, and the gaps between them map the build order exactly.
